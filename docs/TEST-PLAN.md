## 0. 一句话

**停止用"代码反推的测试"证明质量，改用"需求驱动的独立验收 + 可重复的真实浏览器旅程 + 引擎不变量 + 探索式测试"四道闸门；每个用户发现的缺陷都必须变成一条可重复的回归用例。**

## 1. 问题诊断：为什么现在测试全绿，你还能测出问题

### 1.1 现状

- `bash scripts/check.sh` 五项全绿：后端 pytest、ruff、vue-tsc、vitest、vite build。
- 2026-11-11 做过一轮浏览器 E2E（21 项）和 API 场景（19 项），见 `E2E-TEST-REPORT-2026-11-11.md`。
- 引擎纯函数与集成测试覆盖较扎实（状态机、令牌、并行、权限矩阵等）。

### 1.2 四个根因

| # | 根因 | 在本项目中的表现 |
|---|---|---|
| 1 | **Oracle 同源（最根本）** | 测试是看着实现写的，期望值等于代码当前行为。代码把「实例单号」叫成「编号」、把筛选操作符做成「等于」，测试也会跟着断言「等于」——两边一起错，测试永远绿。 |
| 2 | **测试层级错位** | 现有测试集中在引擎纯函数、API、组件挂载；而你测出来的是界面语义、筛选规则、布局、第三方集成、真实操作时序。最近 commit 几乎全是这一类：`90c9250` 列名、`bd4952d` 操作符、`fb5d5fe` 筛选项布局、`ff38193` Univer 画布空白。 |
| 3 | **浏览器 E2E 不可重复** | 上一轮浏览器场景是一次性脚本，报告里明确写「脚本未纳入仓库」。所以每次改动都无法自动回归，只能由你重新人肉探索——你实际上成了唯一的 E2E 测试员。 |
| 4 | **环境与组合缺口** | `b9d9d09` 局域网 HTTP 下 `crypto.randomUUID` 不可用，组件测试在安全上下文里永远通过；Docker 形态「只写完、未实测」；SQLite 开发库与 MySQL/PostgreSQL 目标形态不同；时区、并发、迁移都没有系统验证。 |
| 5 | **需求漂移没有基线** | V1 PRD + 二期 + 三期不断加能力，但"验收点"没有同步成可执行用例；很多歧义（驳回/退回/撤回的边界、谁能看到什么、编号的含义）是在你验收时才暴露的。 |

### 1.3 结论

现有单元/集成测试是**开发护栏**，回答的是"我改代码有没有把已知行为改坏"。
它不回答"这个行为是不是需求要的"，也不回答"真实角色在真实浏览器里能不能走通"。
验收必须另建独立证据链，而不是继续给引擎补单元测试。

## 2. 测试目标与原则

### 2.1 目标

1. 在内部试用前，把 **P0 业务链路的"需求不符"和"数据/权限错误"** 清到可接受水平。
2. 建立一套**可重复执行**的浏览器 E2E 与验收用例，让回归不再依赖人肉探索。
3. 把用户验收从"帮我找 bug"变成"确认业务期望 + 最终签收"。
4. 让每个已修缺陷都有回归用例，防止二次回归。

### 2.2 六条原则

| 原则 | 落地要求 |
|---|---|
| **独立 Oracle** | 验收用例只从 PRD/设计文档/业务规程/用户确认中推导，**设计用例时不读实现源码**；每条用例标明需求来源。 |
| **风险优先** | 先覆盖会导致数据错误、越权、流程卡死、审计缺失的 P0 场景，再谈界面细节。 |
| **在缺陷所在的层测试** | 引擎语义用 API/不变量测试；界面语义、角色旅程、第三方集成用真实浏览器；不拿组件测试冒充验收。 |
| **可重复** | 一条命令拉起环境、重置数据、跑完 E2E；失败有 trace/截图；结果可对比。 |
| **缺陷→用例闭环** | 任何用户发现的 bug，先补一条按期望行为写的失败用例，再修；修完用例转绿。 |
| **用户做产品验收，不做人肉回归** | 你确认"期望结果"和最终 UAT；重复性的回归交给自动化。 |

## 3. 总体策略：四道闸门 + 一个闭环

| 闸门 | 回答的问题 | 手段 | 频率 |
|---|---|---|---|
| **G0 开发护栏**（保留现状） | 改代码有没有破坏已知行为？ | 现有 pytest / vitest / 类型检查 / 构建 | 每次提交 / 收尾 |
| **G1 需求验收** | 行为符合 PRD 和业务期望吗？ | 从需求独立设计的 Given/When/Then 用例；API 黑盒 + 浏览器 | 每轮验收、每个需求 |
| **G2 业务旅程 E2E** | 真实角色、真实数据、真实浏览器能走通吗？ | Playwright 多角色旅程，真实后端 + 独立测试库 | 每日 / 每次合并前 |
| **G3 引擎不变量** | 极端配置和操作序列会破坏状态吗？ | 属性测试 / 模型测试 / 随机流定义与动作序列 |  nightly + 发布前 |
| **G4 探索式与非功能** | 还有什么是我们没想到的？ | 时间盒 Charter、Bug Bash、安全/并发/性能/部署 | 每轮一次 |
| **闭环** | 下次还会犯吗？ | 缺陷分级、根因归类、补回归用例、更新验收矩阵 | 持续 |

**重要**：G0 全绿不能作为验收通过的依据。验收报告只统计 G1–G4 的结果。

## 4. 风险域与优先级

### P0（内部试用前必须覆盖）

| 风险域 | 典型失效 | 后果 |
|---|---|---|
| 认证与数据可见性 | 越权看实例/附件、普通用户调管理接口、设计者看审批数据 | 数据泄露 |
| 流程语义 | 会签/或签聚合错误、条件走错、驳回后卡死、退回重走前序、撤回/终止守卫失效 | 流程错误/卡死 |
| 字段权限与动态字段 | hidden 字段泄露、editable 越权、扩展字段不生效/不落快照 | 数据泄露/数据缺失 |
| 数据完整性 | 重复提交产生双实例/双任务、并发处理覆盖、快照/审计缺失 | 数据错乱 |
| 版本与发布 | 运行中实例被新版本影响、发布校验漏网、锁错表单版本 | 线上事故 |
| 组织与派单 | 部门主管/角色/表单人员解析错误、发起人自审规则、委托/转办错派 | 任务派错人 |
| 检索/归档/导出 | 筛选口径错误、编号混用、导出缺列/越权 | 业务不可用 |
| 环境与部署 | Docker 起不来、MySQL/PG 方言差异、时区偏差、迁移失败 | 无法交付 |

### P1（试用期内补齐）

- 表单/流程设计器的完整配置能力与易用性
- 通知中心、首页聚合、工作量统计/共享表格
- AI 生成的校验、预览、限流与失败兜底
- 打印排版、移动端核心路径

### P2（可延后）

- 视觉细节、极端性能（>1 万实例）、多浏览器像素级一致性
- 非核心管理页的移动端适配

## 5. 独立验收用例怎么来（本方案的关键）

### 5.1 用例来源（按权威性排序）

1. **用户确认的业务期望**（最终 Oracle）
2. `PRD-lowcode-form-approval.md` 的 F1–F8、§9 验收场景
3. `TECH-DESIGN.md` §3–§5（状态机、字段权限、API 契约）
4. `PHASE2/3-DESIGN.md` 的验收点与 DoD
5. `国家融资担保基金数字化平台运维服务项目-项目章程（合稿v2.0）.docx`（真实业务语义）
6. `DEMO.md`、`REQ-OPT-FLOW-CONFIG.md`（现有演示流程）
7. OpenAPI schema（**只看接口契约，不看实现**）

### 5.2 "Spec-only" 用例设计流程

为了让用例不跟着实现走，采用**隔离上下文的独立设计**：

1. **制作 Spec Pack**：把上述文档 + OpenAPI 导出 + 测试账号/数据说明放到一个独立目录，**不包含** `backend/`、`frontend/` 源码。
2. **独立上下文设计**：在新会话/子代理中，只给它 Spec Pack，明确要求"不得读取实现源码"，按固定模板输出用例。
3. **主会话只做执行与修复**：主会话（写过代码的上下文）负责把用例跑起来、定位差异、修 bug，不参与"期望结果"的制定。
4. **用户评审 P0 期望结果**：你只需要确认每条 P0 用例的"期望结果"是否符合业务，不需要看步骤细节。
5. **差异三角定位**：用例失败时，判定是实现 bug、需求歧义还是用例错误；歧义回写 PRD/设计文档，避免下次再争。

> 诚实说明：独立上下文仍然是同一个模型，只能"降低"而不能"消除"实现偏见；最终 Oracle 必须是你和业务文档。这个方法的价值在于**把'代码怎么写'从'应该怎样'里剥离出去**。

### 5.3 用例模板

```markdown
### CASE-ID 标题
- 需求来源：PRD F3.6 / TECH §4.4（必须可追溯）
- 优先级：P0
- 前置条件：角色、组织、表单/流程版本、实例状态、数据
- 步骤：1... 2... 3...
- 期望结果：可观察、可断言（页面文本、状态、API 响应、数据库副作用）
- 验证层：API / 浏览器 E2E / 手工
- 自动化位置：e2e/xxx.spec.ts（或"待自动化"）
```

### 5.4 需求追踪矩阵

维护 `docs/ACCEPTANCE-MATRIX.md`：

| 需求编号 | 验收点 | 用例 ID | 自动化 | 最近结果 | 关联缺陷 |
|---|---|---|---|---|---|
| F3.6 | 驳回后重提轮次+1、旧快照可查 | REJECT-01/02 | E2E | PASS 2026-11-xx | — |
| F4.3 | 并发/重复提交幂等 | TASK-06 | API+E2E | FAIL | BUG-012 |

规则：

- 每个 P0 需求至少 1 条独立用例；核心机制至少 1 条正向 + 1 条反向（越权/非法状态）。
- 矩阵是验收报告的唯一口径；**不用代码覆盖率代替需求覆盖率**。
- 代码覆盖率只作为诊断信息，不作为目标。

### 5.5 防止"测试跟着代码走"的四道检查

1. **Spec-only 设计**（5.2）。
2. **共享测试向量**：公式、字段联动规则已经前后端共用 JSON 向量；继续扩展到"权限/可见性"的期望表。
3. **缺陷→用例**：每个用户发现的 bug 必须先补失败用例；禁止"只改代码不补用例"。
4. **一次性变异审计（可选）**：在引擎里人工注入 20 个语义变异（如把 `any` 改成 `all`、把 hidden 改成 readonly），看现有测试是否变红；变不红说明测试过浅，补用例。比引入完整变异测试工具成本低。

## 7. 浏览器 E2E 自动化方案（Playwright）

### 7.1 选型

用 **Playwright（`@playwright/test`，TypeScript）**：

- 与前端同栈，天然支持多浏览器上下文（多角色同时在线）。
- 自带 trace / video / screenshot、自动等待、webServer 编排。
- 可复用 APIRequestContext 做数据准备，UI 只走关键交互，稳定且快。
- 相比 Selenium/Cypress，跨浏览器与多标签页/多上下文能力更合适本项目的"多角色流转"。

### 7.2 建议目录与运行方式

```text
e2e/
├─ playwright.config.ts
```

### 7.3 环境与数据隔离

- **独立测试库**：`E2E_DATABASE_URL` 指向单独的 SQLite 文件或 Compose 里的独立 MySQL/PG 库；绝不连开发库。
- **独立附件目录**：`STORAGE_ROOT` 指向 `.e2e-storage`，跑完可整体删除。
- **固定种子**：固定组织树、账号、表单、流程；所有 E2E 数据带运行前缀（如 `E2E-<runId>-`），避免并行冲突。
- **重置策略**：测试套件启动时删库→迁移→种子；测试内用 API 工厂自建数据，不依赖执行顺序。
- **账号密码只存在于 E2E 环境**：`SEED_DEMO_ACCOUNTS=true` 仅在隔离环境开启，禁止暴露到可访问网络。

### 7.4 多角色会话

- `global.setup.ts` 用 API 登录一次，保存每个角色的 `storageState`。
- 每个角色 `browser.newContext({ storageState })`，同一测试里并行操作发起人/审批人/抄送人。
- 多角色共享同一个实例时，测试用 `test.describe.serial`；不需要共享的用例保持可并行。
- UI 登录只保留 1 条冒烟用例，其余走 API 登录，减少脆性。

### 7.5 稳定性规范

- 定位器优先 `getByRole` / `getByLabel` / `getByText`，动态表格加 `data-testid`；禁止依赖 antd 内部 class。
- 每步断言用户可见结果（文本、状态、URL），权限类用例同时断言 UI 不显示 + API 403。
- 失败自动留 trace/screenshot/video；`retries: 1`，但**flaky 用例必须修，不能靠重试掩盖**。
- 用例之间不共享可变数据；共享种子只读。

### 7.6 首期必做的 12 条旅程

1. 登录 + 角色菜单冒烟（管理员/设计者/普通用户）
2. 设计者：建表单 → 发布 → 建流程 → 配置节点/条件/权限 → 发布
3. 发起人：发起 → 自动填充 → 草稿暂存 → 提交
4. 审批人：待办 → 修改可编辑字段 → 同意 → 时间线/快照正确
5. 并行会签：两人同时收到 → 一人驳回 → 整单驳回 → 重提轮次 +1
6. 或签：一人同意 → 其余任务取消 → 不可再处理
7. 条件分支：命中/不命中/else 三条路径
8. 字段权限：发起人/审批人/管理员/无关人员四视角（UI + API）
9. 退回指定前序节点 + 撤回/终止守卫
10. 运行中追加字段 → 后续节点可见 → 归档可见
11. 检索/筛选/导出（含动态字段、编号语义）
12. 转办/委托 + 通知/待办同步

移动端与打印先各 1 条冒烟，视觉细节留手工。

### 7.7 不纳入 E2E 的部分

- 纯视觉/排版细节（打印、移动端观感）——人工验收 + 截图对比。
- 复杂拖拽的像素级行为——保留现有组件测试 + 手工探索。
- 第三方 Univer/富文本的内部行为——只测"能加载、能保存、能导出"。

## 8. 引擎不变量与组合覆盖（G3）

现有引擎测试已覆盖已知语义；这一层补的是**不依赖具体实现路径的约束**。

### 8.1 不变量清单

| # | 不变量 |
|---|---|
| 1 | 状态机只允许文档定义的迁移；非法迁移必须被拒绝，且无部分写入 |
| 2 | 任务守恒：每个创建的任务最终处于 待办/已办/取消 之一；无孤儿任务 |
| 3 | 幂等：同一实例+任务+处理人+幂等键的重复请求只产生一次效果 |
| 4 | 并行组只在策略满足时汇合；被取消成员不能再操作 |
| 5 | 权限单调性：hidden 字段永远不出现在无权者的响应/快照/导出/打印中 |
| 6 | 快照一致：每次数据变更都有快照；seq 单调；round 正确 |
| 7 | 审计完整：每个状态变更都有 actor/time/action 记录，且只追加 |
| 8 | 通知正确：每个事件对每个接收人恰好一条；取消/转办后待办同步 |
| 9 | 版本锁定：实例运行期间表单/流程版本不变 |
| 10 | 无 5xx：随机合法定义 + 随机动作序列不产生 500；非法输入返回结构化 4xx |

### 8.2 方法

- **约束生成器**：从合法子集随机生成流程定义（顺序/条件/并行/会签/或签/抄送/填写），再随机生成操作序列（同意/驳回/退回/撤回/终止/重复提交）。
- 每轮检查上述不变量；失败时保留种子和最小复现序列。
- 规模：CI 每次 200–500 轮；发布前 5,000–10,000 轮。
- **变形测试**：加一个不改变业务结果的抄送节点，审批结果应不变；改字段标签不应改变数据；换操作顺序（无依赖时）结果应一致。

## 9. 探索式测试（G4）

自动化覆盖"已知"，探索式覆盖"没想到"。建议每轮 2–3 个时间盒会话，每个 60–90 分钟。

### 9.1 Charter 清单

| Charter | 重点 |
|---|---|
| 发起人在地铁/弱网/连点/刷新/后退下提交 | 幂等、草稿、重复实例、错误恢复 |
| 审批人拿到过期/已取消/别人的任务 | 权限、状态同步、错误提示 |
| 设计者把配置推到极限 | 100 节点、深嵌套、重名、删字段、删分区、空流程 |
| 管理员在运行中改组织 | 部门/角色/主管变更对在途任务的影响 |
| 数据边界 | 空值、超长文本、emoji、特殊字符、0 行/1000 行子表、大附件、重复文件名 |
| 权限穿越 | 直接改 URL/ID、复制他人链接、用低权限 token 调管理接口 |
| 时间与统计 | 跨日/跨时区/月初月末；首页"今日/本周/本月"边界 |
| 故障恢复 | 后端重启、数据库短暂不可用、附件目录不可写、轮询失败 |
| 首次使用 | 新用户能否在无指导下配出第一条流程（可用性） |

### 9.2 启发式检查表

CRUD 完整性、状态迁移、权限矩阵、空/满/异常数据、边界值、并发、时序、失败恢复、文案一致性、默认值、分页/排序/筛选组合、导入导出往返、浏览器前进后退、刷新与多标签。

### 9.3 Bug Bash

- 2–4 小时，你和我在同一环境、用不同角色同时操作。
- 每个问题按统一模板记录（见 §11）；当场分级、去重。
- 结束后 24 小时内给出：去重后的缺陷列表 + 修复排序 + 新增回归用例清单。

## 10. 非功能与环境测试（G4）

### 10.1 安全

- **IDOR**：实例、附件、任务、模板、审计、导出接口逐一用无关用户 ID 访问。
- **角色越权**：普通用户/设计者访问管理员接口；设计者查看审批数据。
- **附件**：白名单、大小、路径穿越、临时附件绑定、下载鉴权。
- **富文本 XSS**：Markdown 白名单；脚本/事件属性/危险协议被清洗。
- **CSV 注入**：导出单元格以 `= + - @` 开头时的处理策略需明确。
- **令牌**：过期、改密、停用、并发登录；刷新逻辑。
- **AI 出网**：默认关闭；只发描述与 schema；限流与审计。

### 10.2 并发与幂等

- 同一用户双击提交 / 多标签页提交。
- 两个会签人同时同意；一人同意同时另一人驳回。
- 并行组两端同时汇合。
- 发起人撤回与审批人同意同时发生。
- 管理员终止与审批人同意同时发生。
- 转办/委托与自动派单同时发生。

### 10.3 性能（先定基线，不追求压测）

| 场景 | 目标 |
|---|---|
| 1,000 / 10,000 实例的归档列表 | P95 < 2s（本地/测试环境） |
| 业务字段筛选 | P95 < 2s |
| 100 节点流程设计器打开 | < 3s，可操作 |
| 工作台待办（100 条） | < 1.5s |
| 首页聚合 | < 1.5s |

用脚本造数（API 批量创建）+ 浏览器 Performance API 或 k6/locust 轻量验证。

### 10.4 环境矩阵

| 维度 | 必须覆盖 |
|---|---|
| 数据库 | SQLite（开发）、MySQL 8（Docker）、PostgreSQL 16（Docker） |
| 浏览器 | Chrome、Edge 最近两个大版本 |
| 视口 | 1440 桌面、390 移动 |
| 时区 | Asia/Shanghai；UTC 存储边界 |
| 部署 | 全新 Docker Compose、重启持久化、附件卷、反向代理 |

### 10.5 迁移与升级

- 从空库执行 `alembic upgrade head`。
- 从上一个发布版本的库升级到 head，抽查关键表与实例可打开。
- SQLite/MySQL/PG 各跑一次核心链路（登录→发起→审批→归档）。
- Docker 形态首次部署必须真实执行一次，记录问题到部署 runbook。

## 11. 缺陷管理与回归闭环

### 11.1 缺陷模板

```markdown
### BUG-xxx 标题
- 环境：分支/commit、数据库、浏览器、账号
- 需求来源：PRD Fx.x / 设计文档章节
- 前置条件：
- 复现步骤：1... 2... 3...
- 期望结果：（引用需求，不引用代码）
- 实际结果：
- 证据：截图/录屏/trace/请求响应/日志
- 严重级别：S1/S2/S3/S4
- 根因分类：需求歧义 / 实现错误 / 界面文案 / 校验缺失 / 环境差异 / 性能
- 回归用例：CASE-ID（修完后必须填）
```

### 11.2 严重级别

| 级别 | 定义 | 示例 | 处理 |
|---|---|---|---|
| S1 | 数据丢失/错乱、越权、流程永久卡死、应用不可用 | 审批后实例状态错、hidden 字段泄露、任务无法处理 | 当天修 |
| S2 | 结果错误但有绕行、权限不符、状态不一致 | 筛选项错、派单错人、导出缺列 | 下一工作日内 |
| S3 | 可用性/文案/布局问题 | 列名歧义、按钮不明显 | 批量修 |
| S4 | 纯视觉/体验细节 | 间距、颜色 | 排期 |

### 11.3 流程

1. 发现 → 按模板记录 → 去重 → 定级。
2. S1/S2：先补**按期望行为写的失败用例**（API 或 E2E），再修，用例转绿。
3. S3/S4：可先修，但必须在矩阵登记；同类问题成批处理。
4. 每轮结束更新 `ACCEPTANCE-MATRIX.md` 和测试报告。
5. 需求歧义导致的缺陷：先更新 PRD/设计文档，再改代码和用例。

### 11.4 度量（只看这几个）

- **P0 需求覆盖率**（矩阵中有用例且已执行的比例）
- **逃逸缺陷数**（验收后由用户发现的数量）及根因分布
- **S1/S2 未关闭数**
- **E2E 通过率与 flaky 率**（目标 ≥98%，flaky <2%）
- **缺陷修复到回归用例转绿的时间**

## 12. 测试环境与数据设计

### 12.1 角色与账号

| 角色 | 用途 |
|---|---|
| 管理员 | 组织/审计/实例管理/终止/追加字段 |
| 设计者（非管理员） | 表单/流程设计、发布；验证无审批数据管理权 |
| 发起人 A（业务部） | 发起、草稿、驳回重提、撤回 |
| 部门主管 A | 自动解析派单 |
| 部门主管 B / 高管 | 多级审批、退回目标 |
| 财务/会签人 1、2 | 并行会签、或签、一人驳回 |
| 填写节点处理人 | 补充字段、动态字段 |
| 抄送人 | 抄送可见不可操作 |
| 无关用户 | 越权与可见性反例 |
| 停用用户 | 登录/令牌失效 |

### 12.2 种子数据

- 组织树：总公司 → 业务部 / 信息部 / 财务部，各设主管。

- 流程：顺序、条件、并行 all、或签 any、会签节点、填写节点、抄送、退回、委托。
- 状态夹具：草稿、运行中各节点、已驳回、已通过、已终止、已撤回、委托中、已归档。
- 所有种子必须走真实发布校验，不允许直接插库造非法定义。

### 12.3 重置

- `scripts/e2e-reset.sh`：删测试库/附件目录 → 迁移 → 种子 → 输出账号表。
- 测试数据统一前缀 `E2E-<runId>-`；套件结束可选清理，失败时保留现场。
- 禁止在开发库/生产库上跑 E2E。

## 15. 现在就开始的三件事

1. **确认范围与节奏**：先按 2 周 P0 快跑，还是直接 4 周全量？P0 清单有没有要增删的业务场景？
2. **建独立 Oracle**：我整理 Spec Pack 和验收矩阵骨架；你在 P0 用例的"期望结果"上签字（尤其是驳回/退回/撤回边界、编号语义、可见性规则）。
3. **建可重复环境**：搭 Playwright 骨架 + 独立测试库 + 种子/重置脚本，先把"登录→设计→发起→审批→驳回重提"这条主链跑成一条命令。

> 原则再强调一次：**以后不再用"单元测试全绿"作为验收结论；验收只认需求矩阵 + 真实旅程 + 你的签收。**
